# Spec: InfiniteChance — 自用 Token 网关 + 无限画布

Status: ready-for-agent

## Problem Statement

我是唯一的用户兼管理员,同时是重度 AI 创作者。我要在多家厂商之间调用聊天、生图、生视频模型:每家鉴权方式、请求格式、计费单位都不一样,密钥散落各处,用量和花费无法归拢;想做「文生图→图生视频→提示词迭代」这类创作流时,只能在各家网页和控制台之间来回手工操作,产物散乱、无法沉淀和复用。

## Solution

一个自用 monorepo 系统,分两半,共用一套 MySQL/Redis:

1. **Token API 网关**:对外暴露统一的 OpenAI 兼容接口(聊天含 SSE 流式、生图同步接口、生视频异步任务接口),内部用适配层对接各厂商原生 API;统一 Bearer key 鉴权、统一错误格式、统一计费与用量记账。配套管理后台提供渠道管理、模型映射、倍率配置、key 发放、额度充值、用量审计。
2. **无限画布**:基于 vue-flow 的创作画布,提示词、图片、视频以节点呈现,连线表达派生关系;生图、生视频、提示词生成、视频反推提示词四类 AI 动作全部经网关完成,不直连厂商;画布自动保存,生成任务服务端编排,产物入素材库。

统一管理后台是一个应用,内分「网关管理」「画布管理」两区。

## User Stories

1. 作为管理员,我想要录入厂商渠道(类型、BaseURL、密钥、模型映射),以便网关能代表我调用该厂商。
2. 作为管理员,我想要启用/禁用渠道,以便故障或欠费的渠道立刻不再被选中。
3. 作为管理员,我想要给渠道配置优先级与权重,以便主力渠道优先、备用渠道兜底。
4. 作为管理员,我想要渠道连续失败后自动熔断、恢复后半开探测自动回来,以便单渠道故障不拖垮整体。
5. 作为管理员,我想要渠道连通性一键测试,以便录入后立刻知道配置是否正确。
6. 作为管理员,我想要维护公开模型名到渠道模型名的映射,以便更换上游时不影响调用方。
7. 作为管理员,我想要创建与吊销 API key、设置额度与过期时间,以便不同用途分开计量。
8. 作为管理员,我想要手工给 key 充值额度,以便自用支出可控。
9. 作为管理员,我想要 key 额度不足时请求被明确的错误码拒绝,以便不会悄悄超支。
10. 作为管理员,我想要查看每个 key 的用量与花费明细,以便知道钱花在哪里。
11. 作为管理员,我想要请求级用量日志(渠道、模型、token/张/秒/条、耗时、状态、扣费金额),以便可审计、可对账。
12. 作为管理员,我想要按天、按模型、按渠道的用量汇总视图,以便一眼看清成本结构。
13. 作为管理员,我想要失败请求也留痕(含上游错误摘要),以便排查渠道问题。
14. 作为 API 使用者,我想要把 OpenAI SDK 的 base_url 和 key 指向网关就能聊天(含流式),以便现有工具零改造接入。
15. 作为 API 使用者,我想要 `/v1/models` 列出可用模型,以便客户端自动发现模型。
16. 作为 API 使用者,我想要生图接口同步返回图片(URL 或 base64),以便像 OpenAI 一样使用。
17. 作为 API 使用者,我想要提交生视频任务拿到任务 id 并轮询查询状态,以便长任务不阻塞调用方。
18. 作为 API 使用者,我想要取消进行中的视频任务,以便不浪费额度。
19. 作为 API 使用者,我想要所有错误都是 OpenAI error object 的形状,以便客户端统一处理。
20. 作为 API 使用者,我想要聊天参数(含 function calling 等高级字段)尽量透传给支持的渠道,以便能力不缩水。
21. 作为 API 使用者,我想要上游临时故障时网关自动换渠道重试,以便偶发失败不打到我的应用。
22. 作为画布后端,我想要用服务级 key 调用网关并在请求上标记画布来源,以便画布用量在网关侧可归属。
23. 作为画布创作者,我想要创建、重命名、删除多张画布,以便不同创作互不干扰。
24. 作为画布创作者,我想要在无限画布上自由添加提示词、图片、视频节点并拖拽连线,以便创作过程空间化。
25. 作为画布创作者,我想要画布自动保存、刷新不丢,以便放心创作。
26. 作为画布创作者,我想要从提示词节点发起文生图,以便文字进入画布变成图。
27. 作为画布创作者,我想要以图片节点为输入发起图生视频,以便一张图变成一段视频。
28. 作为画布创作者,我想要一键根据主题或参考文本生成提示词,以便不用从零写 prompt。
29. 作为画布创作者,我想要对已有视频反推提示词,以便复刻或变体已有效果。
30. 作为画布创作者,我想要生成中的节点显示进行中/成功/失败状态且失败可重试,以便长任务心里有数。
31. 作为画布创作者,我想要生成结果自动入素材库并可跨画布复用,以便成果沉淀。
32. 作为画布创作者,我想要下载生成的图片和视频,以便导出使用。
33. 作为画布创作者,我想要选中节点就能改模型和参数再次生成,以便快速对比效果。
34. 作为画布创作者,我想要关闭浏览器后生成任务仍在服务端继续执行,以便刷新或断线不丢任务。
35. 作为管理员,我想要在管理后台看到画布任务队列与失败原因,以便排查画布侧生成问题。
36. 作为管理员,我想要管理素材库(浏览、删除),以便控制存储占用。
37. 作为管理员,我想要维护提示词模板,以便画布的提示词生成有底稿可依。
38. 作为管理员,我想要 docker-compose 一键拉起全栈(含 MySQL、Redis、对象存储),以便机器重装后快速恢复。
39. 作为管理员,我想要数据卷与数据库定期备份,以便画布与账目不丢。
40. 作为管理员,我想要所有服务都用单管理员账号密码登录、JWT 会话鉴权,以便服务暴露在公网也安全。

## Implementation Decisions

- **Monorepo 四模块**:`gateway/server`(Go+Gin 网关)、`canvas/server`(Go+Gin 画布持久化与任务编排)、`canvas/web`(Vue3+vue-flow 创作前端)、`admin-web`(Vue3 统一管理后台,分「网关管理」「画布管理」两区)。基础设施 MySQL + Redis;Go 侧先按单 module、双入口组织,前端用 pnpm workspace 共享请求层与组件。
- **网关对外契约**:OpenAI 兼容的 chat completions(SSE 流式透传)、models 列表、images 生成/编辑;视频为自定义 OpenAI 风格异步任务接口——提交返回任务 id,轮询查询、可取消。任务状态收敛为五态:queued / running / succeeded / failed / canceled(来自[厂商适配矩阵调研](issues/01-vendor-api-matrix.md);上游的节流态归并 queued、未知态归并 failed)。Bearer key 鉴权;错误统一归一化为 OpenAI error object。
- **厂商适配层**:窄 Adaptor 接口(构造请求 URL、设置鉴权头、请求转换、执行、响应转换并产出用量)。所有 OpenAI 兼容上游共用一个 adaptor;每渠道维护模型名映射。聊天参数 v1 全量透传,渠道不支持的字段由 adaptor 丢弃并在用量日志中标记,不做语义级转换;embeddings、音频等能力不做。
- **转发与韧性**:流式响应透传不重组;仅在请求尚未被上游计费前允许换渠道重试;渠道熔断按「连续 N 次失败才禁用 + 半开探测自动恢复」实现,避免误禁与恢复难(来自[开源网关调研](issues/02-oss-gateway-reference.md))。
- **计费与额度**:双轨计价——聊天按 token 倍率,生图/生视频按次 USD 单价乘尺寸/时长系数;统一支持 token、张、秒、条四种计费单位。扣减采用「按估算预扣 → 完成后多退少补 → 失败退款」;并发安全靠数据库条件更新(额度字段条件扣减)保证不超扣;请求级用量日志记录倍率快照。视频类上游「仅成功计费」,预扣在失败时退款。
- **画布与网关的关系**:画布的全部 AI 动作经 canvas/server 以服务级 key 调用网关,用量通过请求元数据归属到画布来源;canvas/web 不持有厂商或网关密钥之外的直连通道。
- **画布数据模型**:画布图以整图 JSON 持久化(带版本号乐观锁),节点级不入库;自动保存防抖提交。生成任务以任务表驱动、服务端编排,前端断线后可恢复查询;生成产物入素材库(独立资产表,画布节点持有引用)。
- **素材存储**:MVP 采用本地卷存储 + S3 兼容接口抽象,为将来切 MinIO/云 OSS 预留;图片、视频按画布/任务归档,支持签名下载(部署细节由部署票最终定案)。
- **鉴权**:单管理员账号(密码哈希存库),所有管理端与画布端走 JWT 会话;API key 仅哈希存储、支持过期与吊销。
- **配置与密钥**:env 驱动配置;厂商渠道密钥经管理后台录入存库,不进代码库;管理后台初始管理员由首次启动初始化流程创建。
- **视频任务编排归属**:网关负责对上游厂商的任务代理与状态归并;canvas/server 负责画布侧任务编排(并发、重试、与节点的绑定),两层通过网关的视频异步契约衔接。

## Testing Decisions

- 好测试只验证外部行为(HTTP 响应、可见状态变化),不测内部实现细节;绿field 项目无既有测试先例,以本规格为起点建立约定。
- **主缝——两个 Go 服务的 HTTP API**:集成测试直接打路由,厂商上游用内存 fake 替身(OpenAI 兼容聊天/生图 + 异步视频任务替身);MySQL、Redis 用真实实例,以保证原子扣减、任务恢复等真实并发语义被验证。Adaptor 等内部接口不另立测试缝,由 fake 上游间接覆盖。
- **次缝——前端两条 Playwright 冒烟路径**:管理后台「登录→建渠道→发 key→模拟调用→看到用量日志」;画布「建画布→生成提示词→文生图→节点出图」。不做组件级单测铺量。
- 必测的关键行为清单:流式转发与中断、错误归一化、预扣/退款与并发不超扣、渠道熔断与半开恢复、视频任务五态归并与取消、画布自动保存的版本冲突、断线后的任务恢复。

## Out of Scope

- 注册登录、在线充值支付、多租户——自用工具形态排除。
- 画布多人协作/实时协同;移动端适配。
- embeddings、语音、重排序等非聊天/生图/生视频能力。
- 成本告警通知、自动采购/配额联动;生产级高可用与多云部署。
