# 17 画布分析节点

Type: grilling
Status: implemented（按推荐解落地,草案转定案;实现随 17 号票提交）

## Question

「分析节点」的领域定位是什么?输入输出、执行模型(同步动作 vs 画布任务)、模型目录、分析指令来源如何定?与既有「视频反推提示词」(13 号票)的边界在哪?

## Answer

1. **定位:第四种节点类型 `analysis`(分析)**。与提示词/图片/视频平级,分析结果是画布上的持久实体,落在分析节点自身——不是动作的转瞬返回值。与反推提示词的边界:**反推的产出是可复用的提示词**(落提示词节点,直接喂生图/生视频);**分析的产出是对产物的理解**(分镜等结构化记录),供人读、供后续动作引用。两者可对同一视频并存。CONTEXT.md「节点」术语随之更新为四类。

2. **触发与落图:沿用 11/13 号票动作纪律**。视频/图片节点新增「分析」动作(带模型选择),动作先把分析节点与来源节点的连线入图落库(自动保存 flush),再发起同步调用;成功 → 文本写入分析节点;失败 → 分析节点保留、文本为空并横幅报错,空分析节点可原地重新分析或删除。与生成任务「结果节点先落库再提交」同一纪律——分析比反推慢,用户需要看到占位。

3. **节点数据**:`AnalysisNodeData { text: string; model?: string }`(来源派生关系由连线表达,不冗余存引用)。MVP 文本只读展示(pre-wrap + 复制按钮);可编辑与一键「派生提示词节点」留后续。

4. **输入范围**:视频(主场景——分镜分析)与图片。文本输入等其他元素后续票扩展。

5. **执行模型:同步聊天调用,不进 canvas_tasks**。11/13 号票先例:聊天动作无产物素材落库、无取消语义,秒级到分钟级完成,客户端 5min backstop(promptgen Client)兜底;若长视频耗时成为实际问题,再升级为画布任务(kind=analysis,结果仍写节点、不落素材),MVP 不预支该复杂度。来源标记 `gen=analyze`,计费与直连聊天无异(token 轨)。

6. **分析指令:canvas/server 固定常量**(同 `reverseInstruction` 先例,无模板依赖):输出结构化分镜 markdown——分镜表(序号/时间码/画面内容/镜头运动/转场/声音台词)+ 整体风格概述。管理端可配置「分析模板」需要模板系统支持多占位符与模板类型,超出 MVP,后续另立票。

7. **模型目录:复用 `GET /prompt-models`(token 轨)**。qwen-vl 系按 token 计价即出现在目录里;是否真正支持视觉/视频输入由上游裁决,不支持时 4xx 原样透出(13 号票同款决策,网关不设「视觉」能力位)。

8. **接口**:`POST /canvases/:id/analyze`,body `{node_id, media_url, media_kind: "video"|"image", model}` → `{text}`。`media_url` 解析复用反推的引用规则(http(s) 透传 / `/api/assets/{id}/content` 内容寻址解出 / data URI 拒绝 `media_inline_unsupported`),`resolveVideo` 泛化为 `resolveMedia`(kind 按入参校验)。多模态内容分节:video → `video_url`、image → `image_url`,媒体分节在前、指令文本在后(promptgen `userMessage` 同构)。

9. **网关侧零改动**:多模态分节本就全量透传(13 号票已验证 video_url);本票的可用性前提(公网可达的媒体地址、千问渠道与价格配置)见 18 号票。
