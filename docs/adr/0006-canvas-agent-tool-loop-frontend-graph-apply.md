# 画布 Agent 工具循环:事件回传与前端落图

2026-10-31,63-67 号票 grilling 定案。Agent 节点引入真 tool-calling 循环(63 号票),领域工具中「写剧本/写分镜板/落大纲」需要改动画布整图 JSON,由此产生「谁有权写图」的架构取舍。

## Context

画布整图 JSON 至今由前端**独占写**:节点/边的增删改全部经 scene-change → updateNodeData → autosave 链落库,后端只存不写(canvas_tasks 的产物地址回填也由前端任务列表应用到图,后端不碰图)。工具循环若让 canvas/server 直接改库内图 JSON,前端持有的图状态会在下一次 autosave 时整体覆盖后端改动——要么丢工具结果,要么引入图版本号与合并协议,并让后端开始解释节点 schema。

## Decision

1. **循环执行器在 canvas/server,SSE 事件回传**:执行器逐轮调用网关聊天面(`tools` 透传,网关零改动),把工具结果按 `{type:"delta"|"tool_call"|"tool_result"|"done"|"error"}` 事件流推给前端。
2. **工具结果不改库内图**:写图类 tool_result(节点/边草案)由**前端应用**到本地图状态、走既有 autosave——单一写者原则不破;库表类工具(角色/场景/道具读写)由后端经 domain store 直接落库,与图无关。
3. **tool_result 的 payload 结构是前后端契约**(与 SSE 事件协议一起在 63 号票票面定义);后端工具永远只产出「图改动草案」,不解释图 schema。
4. 循环期间浏览器须在线;断线 = 循环中断,已流出文本与已应用图改动保留,可重试(重试从持久历史重建,不带工具帧)。

## Considered Options

- **后端直写图 JSON**:需要图版本/合并机制对抗 autosave 覆盖,后端从此解释节点 schema;唯一收益是「离线续跑」——而对话是在线交互,不值得。放弃。
- **循环全在前端**:前端不持任何密钥(硬性约束 12),LLM 调用必须经 canvas/server 代理;把循环逻辑放前端等于在两侧各写一半执行器,tool 执行(建角色等)仍在后端。放弃。

## Consequences

- 「agent 后台跑任务、关浏览器照跑」的形态与本决策相斥;将来真需要时走 canvas_tasks 式任务化并另立 ADR。
- 前端应用 tool_result 失败(校验拒等)必须在会话内显式报错,不允许静默丢弃(63 号票定案 9)。
- 写图类工具的产物粒度以「前端可原子应用」为准(整节点/整边草案),不做行级 diff。
